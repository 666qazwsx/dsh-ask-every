# Ask-every clarification protocol

在 base-backed profile 的每个会话中注入一条常驻系统提示词协议（section 名 `ask-every-protocol`，order 10400）。协议要求主对话代理按固定三阶段闸门处理任务类消息：

**阶段一：澄清。** 先安静分析并像资深专业人士那样推断真实意图，用一两句话重述理解，然后调用 `ask_user_question` 提出 3–6 个针对真实决策点的问题（含推荐选项、权衡说明）。你的粗略回答会被当作方向性信号折进方案，不会被逐点追问。

**阶段二：计划方向清单（弹窗选择）。** 基于回答起草 2–4 个不同的计划方向，以编号列表展示（每条含一句话目标、关键步骤梗概、主要权衡），随后弹窗让你选择：第一问选方向（单选+可自定义），可能附加一两问方向内细节。

**阶段三：执行闸门。** 每次计划方向清单弹窗的最后一问固定为：「这份计划方向清单是否满足你的需求？是否开始执行任务？」选项为「满足，开始执行（推荐）／需要修改（自定义输入说明改哪里）／还有遗漏，我要补充需求」。
- 选「需要修改」→ 修订清单后再次弹窗（同样以固定最后一问收尾）；
- 选「还有遗漏」→ 回到阶段一补问新缺口；
- 修改轮次超过 3 轮后，只聚焦剩余分歧点（至多 3 问），不再整单重列；
- 只有明确选择「满足，开始执行」任务才启动；跳过/超时不作数，会简化后重发一次清单。

子代理、团队任务执行者、定时任务消息、goal 自动续跑不受协议约束。闲聊、确认续行、元问题不触发弹窗。用户随时可以说"别问了/你定吧"跳过当前任务。

## 配置（cordis.patch.yml 的 `ask-every` 行）

| 字段 | 默认 | 说明 |
|---|---|---|
| `minQuestions` | `3` | 阶段一最少提问数 |
| `maxQuestions` | `6` | 阶段一最多提问数 |
| `reaskOnSkip` | `true` | 弹窗被跳过/超时视为未放行，简化后重发清单；改 `false` 则转为"声明假设后继续" |
| `dimensions` | plan-first 五类 | 阶段一追问维度清单（goal/scope、audience/scenario、deliverable form、hard constraints、edges/failure），数组，可增删改写成任意语言 |
| `extraRules` | `''` | 追加到协议末尾的自定义规则文本 |

## 已知边界

- 提示词层约束：协议靠模型遵循系统提示词来生效，不是引擎级硬闸；极端情况下模型仍可能直接作答。
- 对普通 DSH 会话生效（需安装后重启/新会话）。已存在的旧会话从下一条消息起同样生效。

## 卸载 / 回滚

在 Plugins 面板禁用 `ask-every` 行，或整包移除 `dsh-ask-every`；也可直接删除工作区插件目录 `dsh-ask-every\`。
